# 日志库同图语义去重 + 容量上限设计

日期：2026-08-09
状态：已批准（用户确认方案 A + 三个决策点）

## 1. 背景与问题

日志库（`agent/data/rag_feedback_logs.csv` + Chroma 向量集合 `rag_test_logs`）的定位是**高正确率提炼集**：运行期每次会话产生一条记录进暂存区，`flush_pending_logs.py` 批量入库；查询侧命中日志即高置信度返回（隶属度 = 0.9×相似度 + 0.1×正确率，≥ fit_threshold 0.65）。

**问题**：入库查重键是 `(图片id, question)` **精确字符串匹配**（`log_manager.py:30-32` 的 `record_key`）。同一张图同一问题换个说法（paraphrase），会被当作两条独立记录入库：
- 日志库随问法变体冗余膨胀，一份知识变成 N 条近重复向量；
- 查询命中时近重复条目全部达标、全部塞进 LLM 上下文，重复占用 token；
- 违背"提炼汇聚"定位。

**数据实测（2026-08-09）**：
- 日志库 **14,441 条**（全为 correct=1），覆盖 11,478 张图（每图中位数 1 条）；切片库 180,374 条。
- 同图问题对字符串相似度 p99=0.63，**语义相似度 p99=0.860、max=0.884**（bge-m3，抽样 400 对）→ 存量库内没有问法变体冗余（基准测试题本身问题各异），且 0.92 阈值下**零误合并**。
- 1.5× 切片库上限 ≈ 27 万条 → 当前库仅占 5%，**首次运行淘汰 0 条**。

**结论**：去重机制是为**在线积累**的问法变体准备的保险（防未来膨胀），不用于治理存量（存量没有膨胀）。上限是长期保险丝。

## 2. 设计决策（已确认）

| 决策 | 结论 |
|---|---|
| 去重粒度 | **同图内**（id 相同 + 问题级相似度 ≥ 阈值才合并）；不同图相同问题各自保留（不同场景，答案不同） |
| 合并保留 | **高分优先**：新分更高 → 整体替换（问题文本用新的）；同分 → 保留时间戳更新的一条；新分更低 → 丢弃 |
| 容量 | **硬上限 + 淘汰**：`max_log_records`（0 = 自动 = 1.5× 切片库条数）；超限按 `(correctness_score 升序, timestamp 升序)` 淘汰尾部 |
| 相似度判定 | **问题级余弦相似度**（非文档级）；阈值默认 0.92，可配置 |

**为什么必须用问题级相似度**：日志向量是「问题+切片内容+回答」综合向量（`build_log_doc_text`，`log_manager.py:98-113`）。同图两条记录共享几乎相同的切片内容（每片 200 字符、合计 1500 字符），文档级相似度会被共享内容推高——会把"同图上的两个完全不同的问题"误判为重复。实测同图不同问题的问题级相似度最高已达 0.884，文档级只会更高，故合并判定必须落在问题级、阈值必须高（0.92）。

## 3. 技术设计

### 3.1 入库流程（`flush_pending_logs.py` 改造后）

```
pending 记录补齐切片内容
   │
① 批量内语义去重：新记录之间，同图 + 问题级相似度 ≥ 阈值 → 合并取最高分
   （batch ≤ 阈值(默认50)，两两比较成本可忽略）
   │
② 对每条剩余新记录：
   a. 用 question 嵌入查询日志库 ExactVectorIndex top-5（文档级向量，快）
   b. 过滤：同 id + 预筛相似度 ≥ 0.80
   c. 对候选的 question 重新嵌入，算问题级相似度 ≥ 0.92 → 判定语义重复
   │
③ 合并决策（复用现有决策表语义，log_manager.py:41-95）：
   新分更高 → replaced（整行替换；向量按旧键删除后重写新向量）
   同分 + 时间戳更新 → replaced
   新分更低 → dropped
   │
④ 精确匹配共存：新记录与某行问题完全相同的 → 精确匹配路径优先
   （同问题字符串是更强信号，语义路径不覆盖）
   │
⑤ 上限淘汰：len(log_df) > max_log_records → 按 (score 升序, ts 升序) 淘汰尾部
   │
⑥ 写 CSV → 向量库 upsert（删除：被替换旧向量 + 被淘汰记录向量）→ 备份清空暂存区
```

### 3.2 判定逻辑细节

- **候选检索**：复用运行期同一组件 `ExactVectorIndex`（`exact_index.py`，faiss 全量精确，`cache_system.py:50` 已用于日志库）。14k 条规模导出向量约 60MB、秒级完成；查询时只嵌入新问题（每次 flush ~50-100 次嵌入，27s/768 条实测）。
- **预筛阈值 0.80**：只对文档级相似度 ≥ 0.80 的同 id 候选做问题级复核，省嵌入；0.80 以下同图问题几乎必非重复（语义分布 p99=0.86 且有共享内容加成）。
- **阈值可配置**：`dedup.sim_threshold` 默认 0.92（实测校准：0.92 下存量 14k 库零误合并；0.85-0.88 会大量误合并，禁止下调至此区间）；`dedup.pre_filter` 默认 0.80。
- **语义重复指向现有行**：`find_semantic_duplicates` 返回 `(新记录 → 现有行索引, 问题级相似度)` 映射；replaced_keys 必须携带**旧行的 (id, question)**（`generate_log_vector_id` 依赖它定位删除，`log_manager.py:35-38`）。

### 3.3 上限淘汰

- `max_log_records`：0（默认）= 自动 = `round(1.5 × SliceStore().count())`；正整数 = 硬上限。
- 淘汰排序 `(correctness_score 升序, timestamp 升序)` → 低分最旧先淘汰，符合"高正确率提炼集"定位。
- 淘汰记录同时从向量库删除（`generate_log_vector_id` 定位）。
- 当前规模下永不触发（14.4k ≪ 270k），是长期保险丝；首次启用不产生大规模数据删除。

### 3.4 改动文件

| 文件 | 改动 |
|---|---|
| `agent/rag/membership/log_manager.py` | 新增纯逻辑函数 `find_semantic_duplicates(existing_df, new_records, logs_index, embed_fn, sim_threshold, pre_filter)` 与 `enforce_log_cap(df, max_records) → (df, evicted_keys)`；`merge_log_records` 增加可选语义路径参数 |
| `agent/data/flush_pending_logs.py` | 编排：构建日志 ExactVectorIndex → 批量内去重 → 语义查重 → 合并 → 上限淘汰 → 向量 upsert + 删除（被替换 + 被淘汰） |
| `agent/rag/core/config.py` + `config/chroma.yml` | `dedup.sim_threshold`(0.92) / `dedup.pre_filter`(0.80) / `dedup.max_log_records`(0=自动) |

### 3.5 边界情况

- 新记录同图候选在精确匹配路径已处理 → 精确优先，语义路径跳过该记录。
- 批量内两条新记录都映射到库内同一行 → 各自按决策表与旧行比较，保留最优结果（两次比较串行覆盖，天然幂等）。
- 向量库写入失败 → 保留 pending 不清空（现有设计条款不变，CSV 已更新可接受，重跑幂等）。
- 嵌入/检索异常 → 语义去重整体降级为"仅精确匹配"，记录 warning，不阻断入库。

## 4. 测试计划

1. **纯逻辑单测**（合成数据，不触库）：
   - `find_semantic_duplicates`：同图高相似 → 判定重复；同图低相似 → 不判；异图同文本 → 不判；精确匹配共存时语义路径跳过。
   - 决策表三分支（replaced / 同分保新 / dropped）。
   - `enforce_log_cap`：超限裁尾、返回被淘汰键。
2. **端到端冒烟**：临时 `log_path` 覆盖跑一次 `run_flush`（构造含 paraphrase 对的 pending 样本），校验 新增/替换/丢弃 计数、CSV 与向量库一致（替换后旧向量删除、新向量可检索）。
3. **阈值回归**：抽样 400 对实测（本设计已做，max=0.884），确认 0.92 下无合并误判。

## 5. 非目标

- 暂存区 append 时去重（在线路径引入嵌入延迟，暂存区是瞬态缓冲，不做）。
- 定期全库去重扫描（全库重嵌入成本高；增量去重已覆盖新数据，存量无冗余）。
- 修改运行期隶属度命中逻辑（hit 阈值 0.65 保持不变）。
